## 2. Key workflow: Admission to enrollment

1. Admission officer creates an inquiry.
2. Parent/guardian submits application and documents.
3. Admission team reviews eligibility and assessment.
4. Authorized user approves or rejects application.
5. Student record is created or linked without duplicating a person unnecessarily.
6. Guardian and household relationships are linked.
7. Student is assigned to a school, campus, academic year, class and section.
8. Fee assignment is created by the Fees module according to the approved fee plan.
9. Parent receives enrollment confirmation and next steps.

**Controls:** Duplicate student detection, required-document checks, approval history and permission enforcement.

## 3. Key workflow: Fee payment and accounting

1. Invoice is generated by Fees.
2. Cashier selects the student/household and invoice(s).
3. Payment method and amount are entered.
4. Fees validates the allocation and creates a payment record.
5. Finance creates the corresponding balanced accounting journal through an approved integration contract/event.
6. Receipt receives a unique identifier and status.
7. Communication sends a receipt notification asynchronously.
8. Audit records the actor, time, device/source and action.

**Rules:**
- A payment can be allocated across multiple invoices, including siblings, where authorized.
- An invoice can receive multiple partial payments.
- A payment allocation cannot exceed the amount available for allocation.
- Posted financial records are not silently deleted or edited.
- Corrections use reversal/adjustment entries with approval and reason.
- Receipt state must distinguish provisional offline receipt from server-confirmed receipt.

## 4. Key workflow: Bank reconciliation

1. Accountant imports a supported bank statement.
2. Reconciliation records the import batch, source file metadata and normalized rows.
3. System checks for duplicate import and duplicate bank references.
4. Matching engine generates candidates based on amount, reference, date, payer details and other approved features.
5. High-confidence suggestions can be shown for authorized review; low-confidence transactions remain unmatched.
6. Accountant confirms allocation to one or more invoices/payments.
7. Fees and Finance modules perform their own authorized operations through contracts.
8. Reconciliation session is closed only when its totals and exceptions are accounted for.
9. Audit retains the source, match decision, reviewer and changes.

**Important distinction:** A bank statement credit is evidence of a bank transaction, not automatically proof that a specific student's fee invoice has been correctly allocated.

## 5. Key workflow: One payment for multiple siblings

Example only: a parent transfers PKR 30,000 for two children.

- Bank transaction amount: PKR 30,000.
- Child A allocation: PKR 15,000.
- Child B allocation: PKR 15,000.
- Sum of allocations must equal the amount allocated from the transaction.
- The system records the family/guardian relationship and each invoice allocation.
- Each child’s fee ledger is updated through the Fees module.
- One source bank transaction remains linked to both allocations.

## 6. Key workflow: Offline attendance

1. Authorized teacher signs in while online and downloads a minimal assigned-class dataset.
2. Device registration and scope are checked.
3. Teacher records attendance offline.
4. Client creates a unique operation ID and stores the event locally.
5. UI displays Pending Sync, not Synced.
6. On connectivity/reopen, client sends queued events.
7. API authenticates user and device, checks tenant/campus/class scope, validates the event and applies idempotency.
8. Server acknowledges success or returns a conflict/validation error.
9. Client updates local sync state and preserves reviewable failures.

## 7. Key workflow: Examination result approval

1. Examination controller configures an exam and subjects.
2. Teachers enter marks.
3. Validation checks required entries, grading rules and anomalies.
4. Authorized reviewer/moderator reviews changes.
5. Result is approved and locked according to policy.
6. Report cards are generated.
7. Parent/student access is enabled according to publication rules.
8. Later corrections require a controlled recheck/amendment process.

## 8. Key workflow: AI-assisted action

1. User enters a request or starts an AI tool.
2. Backend identifies user, tenant, campus and permission scope.
3. AI module fetches only the minimum approved data through application services/reporting tools.
4. AI produces a structured suggestion with evidence and model/prompt metadata.
5. User reviews the suggestion.
6. For a permitted action, backend validates and executes a normal business command.
7. Human approval is required for sensitive financial and academic outcomes.
8. AI request, output reference, review and final action are audited.


## Platform-level modules added for Hybrid deployment (v1.1)

These modules live in the Cloud Control Plane and are separate from school operational modules:

- Tenant Registry and Customer Onboarding.
- Subscription Plans, Billing and Payment Verification.
- Entitlement and Feature Plan Management.
- License Signing, Lease Issuance and Revocation-on-next-contact.
- Local Node Registry and Activation.
- Cloud Sync Hub, Node Cursors and Event Routing.
- Signed Release/Update Management.
- Optional Backup Catalogue and Cloud Reporting Projections.

The Local Data Plane contains a license verifier, local entitlement snapshot, local Sync Agent and local backup/update agents, but never the cloud license signing private key.
